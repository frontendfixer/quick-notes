# Quick Notes implementation proposal

Research reviewed on 2026-11-18. Quick Notes is a private, installable notes PWA for Android and Linux. The first release prioritizes recovering writing, responsive editing, and access to locally available notes offline. PostgreSQL holds the server copy. Each device keeps a bounded cache of opened notes and retains all unsynchronized work independently of that cache.

## Stack and compatibility

| Area | Proposed baseline and verification |
| --- | --- |
| Frontend | Start with Solid 2.0, TypeScript, Vite 8 and SCSS via Sass. Solid’s release page identifies 2.0 as latest, and Vite documents a Solid TypeScript template and its Node requirements. Use a supported Node LTS for the build. Verify the published Solid compiler, web runtime and plugin as a set before locking versions. [Solid releases](https://github.com/solidjs/solid/releases), [Solid Vite plugin](https://github.com/solidjs/solid-vite-plugin), [Vite guide](https://vite.dev/guide/) |
| Editor | Tiptap 3 core with matching ProseMirror dependencies and a small Solid lifecycle integration around the vanilla Editor API. Mount once per open note and destroy on cleanup. Let ProseMirror own the editable DOM and use Solid for toolbar and save status. Use scoped extensions for bold, italic, underline, strike, headings, bullet and numbered lists, task lists, highlight, links and undo/redo. Verify composition, selection, clipboard behavior and JSON round trips. [Tiptap vanilla integration](https://tiptap.dev/docs/editor/getting-started/install/vanilla-javascript), [Tiptap lists](https://tiptap.dev/docs/editor/extensions/lists), [ProseMirror view](https://github.com/ProseMirror/prosemirror-view) |
| API and database | Use Hono on Bun, Drizzle ORM and Kit on stable release lines, and PostgreSQL 18 with current minor updates. Bun docs show 1.4.4. Prefer the native Bun SQL adapter if a stable release passes concurrent writes, transaction rollback, timestamp/JSON mapping, TLS and migration checks. Drizzle’s Bun guide installs release candidates, so validate the published stable adapter independently. If it fails, test Drizzle’s node-postgres adapter under Bun before considering a runtime change. [Hono on Bun](https://hono.dev/docs/getting-started/bun), [Bun SQL](https://bun.com/docs/runtime/sql), [Drizzle Bun SQL guide](https://orm.drizzle.team/docs/get-started/bun-sql-new), [PostgreSQL version policy](https://www.postgresql.org/support/versioning/) |
| Offline shell | Use the published Vite PWA plugin with Workbox-generated precaching and a user-controlled update prompt. Verify its peer range with the selected Vite version and ensure the editor chunk launches offline. Cache the shell and immutable assets. Route authenticated requests directly to the network. [Vite PWA update guide](https://vite-pwa-org.netlify.app/guide/prompt-for-update.html), [Plugin repository](https://github.com/vite-pwa/vite-plugin-pwa) |
| Storage and transport | Use IndexedDB behind a small transaction interface, native fetch, and shared TypeScript/Zod validation for API boundaries. Treat a completed IndexedDB transaction as the local save milestone. Request persistent storage where supported and expose failures and recovery export. [IndexedDB completion](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event), [Storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) |

The review establishes documented integration paths. Exact package pins, peer resolution and runtime behavior remain to be verified in the first phase. Record the selected versions and commit a lockfile then.

## Architecture and data

Use a small workspace with `apps/web` for Solid, the editor, local storage and sync; `apps/api` for Hono, auth, queries and migrations; and `packages/contracts` for request and response schemas. Serve the static build and `/api` under one HTTPS origin. Keep one PostgreSQL database with a restricted application role and a separate migration role. Apply reviewed migrations before deploying dependent code. Keep old static chunks available across deploys, maintain backward-compatible API and IndexedDB during updates, and exercise database backup restoration in staging. Log timings and failure categories without including note bodies, search text, or credentials.

Use client-generated UUIDs for offline creation. Each note stores its owner, title, versioned Tiptap JSON, derived search text, timestamps, pin/archive state, soft-delete timestamp and monotonic revision. Every state mutation advances the revision. Keep deleted rows restorable in v1. Index owner and list sort keys and use a GIN-backed search vector derived from title and editor text, initially using PostgreSQL’s simple text configuration. Check tokenization on representative notes before finalizing. Use a stable sort with an ID tiebreaker and cursor pagination. [PostgreSQL text search indexes](https://www.postgresql.org/docs/current/textsearch-indexes.html)

| API | Contract |
| --- | --- |
| `GET /api/notes` | Owner-scoped summaries with active, archived or trash filter, query, sort and cursor. Active notes can show pinned first. |
| `GET /api/notes/:id` | Full document and revision, using conditional requests for refresh. |
| `PUT /api/notes/:id` | Create or update with an immutable mutation ID, expected revision (null for create), and validated editable fields. Return the acknowledged mutation ID and revision. Return 409 with current state on revision mismatch. |
| `GET /api/export` | Account-scoped, versioned JSON backup with document and metadata. Provide a local recovery download for pending drafts and conflicts, including offline. Include a documented restore procedure and a round-trip fixture. |

Validate size, nesting, supported nodes and marks, and safe link protocols on the server. Scope every query, mutation receipt and export to the authenticated owner. Persist the mutation ID, payload fingerprint and result in the same transaction as the revision-checked update. On replay return the original acknowledgement, even if the note has advanced. Reject reuse with a different payload. Retain receipts in v1 so delayed retries can recover across long offline periods.

## Autosave, offline, and refresh

1. Update the editor immediately. Serialize changed content promptly outside the input handler in a short, bounded batch. Queue IndexedDB writes in order for each draft. Keep dirty content in memory on failure and offer retry or download. Show **Editing** until the transaction completes, **Saved on device** after commit, and **Saved to server** once the latest local generation is acknowledged. A process kill before commit can lose the pending keystrokes. Test that window and minimize it.
2. Store clean snapshots separately from draft lineages and immutable in-flight mutations, scoped by account and note. Keep the open note and a small recent cache, initially 20 clean notes. Never trim unacknowledged or conflicting drafts. A new offline session can open the locally available list. Server search remains available when connected.
3. Debounce uploads independently of local writes. Persist the sent payload, base revision, mutation ID and generation before sending. Retry that same payload after a timeout or restart, with capped backoff. On acknowledgement, update the relevant draft lineage transactionally. Clear only the acknowledged generation. A newer generation in the same lineage advances to the acknowledged base and remains queued. Use distinct lineages for independently opened editors, with recovery entries for both if the same note is edited in multiple tabs. Deduplicate retries at the server and avoid relying on tab coordination for correctness.
4. On startup, focus, reconnect and every 60 seconds while visible, resume pending uploads and refresh the visible list and open note. Coalesce overlapping triggers. Apply fetched state only when it is at least as fresh as the snapshot and the active editor is clean. Recheck account, note, draft generation and revision before applying delayed responses. Defer editor replacement during composition. Treat connectivity events as hints and handle fetch errors normally. [Chrome page lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)
5. On conflict, keep the server version and the local draft. Offer viewing both, saving the draft as a new note, downloading it, or explicitly applying a reviewed version against the current revision. Pause that lineage until resolved. Authentication expiry pauses upload and prompts reauthentication while preserving the local draft. Show storage failures, conflicts and suspended uploads in the save status. Activation of an updated service worker waits until current edits are locally committed or the user defers the update.

IndexedDB persistence reduces eviction risk when granted. Users can clear site data, and browser storage is tied to the origin and profile. Force-close recovery must be verified on installed Android Chrome and desktop Chromium on Linux, including after app updates. [Browser installation model](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Installing), [Browser storage limits](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## Authentication and device policy

For an initial personal deployment, provision accounts privately and use Better Auth with a database-backed session, mounted on Hono. Start with email/password plus an operator-assisted recovery path for the private deployment. Use HTTPS, HttpOnly and Secure cookies, SameSite=Lax, exact trusted origin validation on mutating requests, session revocation, and rate limits on login. Verify the chosen adapter and migrations in the compatibility phase. Public signup and self-service account recovery would require a separate product decision and provisioning flow. [Better Auth Hono integration](https://www.better-auth.com/docs/integrations/hono), [Better Auth sessions](https://www.better-auth.com/docs/concepts/session-management)

Assume offline access is for a trusted device previously signed in. An expired session can continue editing locally in that profile. Explicit sign-out hides all offline content and warns about pending work, offering sync or download before sign-out. Retain any remaining pending drafts under their original account and require online authentication as that account before exposing them again. IndexedDB does not provide a separate protection boundary from a user with access to that browser profile. A shared-device requirement would change the offline access policy.

## Phases and release gates

| Phase | Acceptance criteria |
| --- | --- |
| 0. Compatibility | Pin supported versions after a clean install, typecheck and production build. Exercise the editor with Android composition input, install the generated PWA on both platforms, and run the selected DB driver through concurrent writes, rollback, TLS and migrations. Confirm auth issuance, expiry and revocation. |
| 1. Private notes | Account isolation holds for single-note access, lists, search, writes and export. Online flows cover create, edit, archive, pin, soft-delete and restore. Search and paging remain stable with thousands of seeded notes and deterministic tie-breaking. All requested formatting survives save/open and backup restore. |
| 2. Local durability and convergence | Edit three notes offline, switch repeatedly, force-close after local-save status, reopen offline and recover every draft. Reconnect and upload all drafts. Inject dropped acknowledgements, reversed responses, parallel tabs/devices, revision conflicts including remote deletion, expired sessions, quota errors and app updates. Assert that each committed local edit is either acknowledged or recoverable and stale requests never replace newer work silently. Test first launch with no network and no cached shell as a distinct condition. |
| 3. Release checks | Verify installed Android Chrome and Linux Chromium on actual hardware. Test Gboard composition, autocorrect, selection, checklist taps, links and rotation. Test desktop keyboard editing and navigation, focus order, screen reader save messages and light/dark contrast. Verify deployment roll-forward, export and database restore. |

### Initial performance budgets

Use production builds on a midrange Android device and a Linux desktop. Record browser/device versions and run 20 samples for cold first visits, installed cold starts with a cached shell, and warm interactions. Use representative 10 KB and 100 KB rich-text documents and fixed network conditions. Track separate measurements for first paint, editor readiness, local commit and server acknowledgement.

- Initial shell JavaScript at most 100 KiB compressed, with the editor as a lazy chunk included in offline precaching.
- P95 installed cold start to interactive list at most 1.5 seconds and cached note opening at most 300 ms after shell readiness.
- P95 typing interaction to next paint at most 50 ms and final input to local commit at most 250 ms during normal foreground editing.
- On a healthy connection target P95 final input to server acknowledgement at most 2 seconds, measured separately from offline retries.

These are proposed release targets. Record baseline measurements in phase 0 and tune caching, editor serialization and refresh cadence against the results.
